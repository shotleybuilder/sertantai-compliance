# Plan: v0.1 Production Release for QQ

**Created**: 2026-09-25
**Deadline**: 2026-10-31 (QQ's ENHESA contract ends)
**Target tag**: `v0.1.0` ~2026-10-27 (buffer to 31 Oct)
**Sessions**: [`.claude/sessions/v0.1/meta.md`](../sessions/v0.1/meta.md)

## Goal

Ship a production screener that QQ users rely on to **keep abreast of legal change**, and that **exceeds QQ's expectations** at first sight. There will be no second chance at a first impression.

QQ is moving to a single org-level legal register. They are building compliance assessment into an existing tool for now. SertantAI's job in v0.1 is to be the source for:

1. **What applies to us**: the applicability screener, which builds the org register.
2. **What changed**: status changes, new laws and repeals affecting the register, with review due dates.

## Scope

### In
- Profile wizard, including the context-first profiler as a stretch goal (see gate below)
- Screener results: confidence tiers, match reasons, applicability tree, provision drill-down
- Org register: accept/exclude and the activity trail
- **Change feed** (`/app/changes`): status changes, new matching laws, review workflow
- Browse and glossary pages (already built)
- Dashboard stats. The Screener Gaps drill-down (#23) is optional for users, but it is the internal accuracy diagnostic.

### Out (post v0.1)
- Baserow sync. QQ is doing assessment in its own tool.
- Register access control / capabilities (fitness 04, blocked on auth#20 and hub#22). v0.1 treats all QQ users as trusted register editors.
- "What If" scenarios (#20)
- Per-site modelling (see below)
- AI assessments

## Key decisions

| Decision | Rationale |
|----------|-----------|
| **Org-and-decompose model** | QQ is migrating to a single org legal register. v0.1 uses one QQ org profile evaluated against the whole corpus. Later we decompose to sites (22 sites: 14 England, 5 Scotland, 3 Wales). Eventually we support both directions: granular→aggregate and org→decompose. Don't design anything that blocks site decomposition, for example by hard-coding one profile per org in new code. |
| **Accuracy is measured, not eyeballed** | A repeatable benchmark (`mix screener.benchmark`) against QQ's known register drives every data fix. Manual QA sessions sit on top of it. |
| **Recall over precision** | Missing an applicable law is worse than surfacing an irrelevant one. Target ≥95% recall on in-force Making laws in QQ's register, and every remaining FP must have an explanation. |
| **Data fixes happen in sertantai-legal** | Compliance consumes. The backend work list lives in sertantai-legal#161. |
| **SemVer 0.x, tagged releases, immutable images** | This is the first tagged release in the ecosystem, so it sets the convention for legal, hub and auth. |

## Release practices (set up in week 0, used from rc.1)

- **Versioning**: SemVer, staying on `0.x` until the API and data are stable. `backend/mix.exs` and `frontend/package.json` always carry the same version; `scripts/release.sh X.Y.Z` bumps both.
- **Changelog**: `CHANGELOG.md` in [Keep a Changelog](https://keepachangelog.com) format, with an `Unreleased` section. Commits are already conventional-style, so `git-cliff` drafts the entries and a human edits them into customer-readable language.
- **Tags & releases**: annotated `vX.Y.Z` tag on `main` and a GitHub Release with the changelog section. Pre-releases are `vX.Y.Z-rc.N`.
- **Images**: tag every image `:X.Y.Z` and `:sha-<short>`. Prod deploys a pinned tag, never `:latest`. Rollback means redeploying the previous tag.
- **Milestone**: GitHub milestone `v0.1` holds every in-scope issue.
- **Runbook**: `docs/RELEASING.md` checklist, in this order:
  1. CI green
  2. changelog
  3. version bump
  4. tag
  5. build/push images
  6. **DB backup**
  7. schema before data
  8. deploy pinned tag
  9. smoke test
  10. GitHub Release
- **After v0.1**: propose the same convention to sertantai-legal, hub and auth.

## Risks

| Risk | Mitigation |
|------|-----------|
| Legal-side data work slips; nobody has worked on screening data since mid-July | Legal issue with a prioritised list. Benchmark drives priority: fix what moves QQ's numbers, not the whole corpus. |
| legal#133 prod migration goes wrong | DB backup first. The issue has a documented stopgap: rewrite `legal_register`→`uk_lrt` in the compliance proxy. |
| Change feed empty or noisy at launch | Wire the trigger early (week 1). Seed a baseline checkpoint so QQ doesn't get flooded with historic "changes" on day one. |
| Cross-user data leak via shared IDB | Audit and fix in hardening. Must be done before any second QQ user logs in. |
| Auth/hub not ready for real users | Verify the login end to end with a real QQ user account in week 3, not on launch day. |
